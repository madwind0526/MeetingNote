# Roadmap (다음에 할 일)

> 사용자가 2026-08-17 세션 마지막에 구술한 향후 기능 목록. 아직 설계/구현 전 - 순서는 사용자가 부른
> 순서 그대로이고 우선순위 순서는 아님. 다음 세션 시작 시 이 목록부터 검토할 것.

## 1. 약어 사전 등록 → 회의 중 약어 치환

회의 중 나오는 약어를 사용자가 등록해두면, 그 약어를 (아마 회의록 생성 시 또는 대본 표시 시) 원래
용어로 치환. 저장 방식(용어집 UI/데이터 모델), 어느 단계에 적용할지(STT 원문 자체를 고칠지, LLM
회의록 생성 프롬프트에 사전으로 같이 넣을지, 화면 표시만 치환할지) 미정 - 다음 세션에서 사용자와
확인 필요.

## 2. 발표 자료 → MD 변환 + STT 대본과 합쳐서 발표 내용 정리 (LLM)

Agenda/A-I List에 등록된 발표 자료(`materialPath`, PDF/DOCX/PPTX)를 읽어서 MD로 변환하고, 그 시간대의
STT 대본(`transcriptSegments`)과 합쳐서 LLM으로 "이 발표에서 실제로 무슨 얘기가 오갔는지" 정리.
- 자료 텍스트 추출은 기존 `server/parsers/importPdf.mjs`/`importDocx.mjs`/`importPptx.mjs`의 텍스트
  추출 로직을 재사용할 수 있을 듯(단, 지금은 "라벨 형식 회의록"을 파싱하는 용도라 순수 텍스트 추출
  부분만 떼어 써야 함).
- "이 발표 자료가 어느 Agenda/A-I 항목에 속하는지"와 "그 항목이 실제로 몇 시~몇 시에 발표됐는지"를
  연결하는 방법이 필요(현재 데이터 모델엔 Agenda 항목과 발화 시간 구간을 잇는 필드가 없음).

## 3. 발표 내용을 합쳐서 전체 회의록 작성

2번에서 나온 발표별 정리를 모아 전체 회의록으로 합성. 기존 `server/llm.mjs`의
`buildMinutesPrompt`/회의록 작성 흐름을 확장하는 형태가 될 듯.

## 4. 회의 중 나온 A/I 정리 (항목 + 담당자 + 기한)

지금 `actionItems`는 "회의 전 사전 계획된" 항목만 다룸(폼에 사용자가 직접 입력). 이건 **회의 도중에
새로 언급된** action item을 대본에서 LLM으로 뽑아서 항목/담당자/기한까지 구조화하는 것 - 별도
필드(`minutes` 안에 텍스트로 녹일지, 구조화된 새 필드를 domain.ts에 추가할지)부터 정해야 함.

## 5. 발표자/참석자 목록에 없는 임의의 인물이 발언하는 경우 처리 방안

회의 중 사전 등록 안 된 사람(게스트 등)이 말할 수 있음 - 아직 **설계가 안 된 질문**, 기능이 아님. 현재
상태: `diarizeSegments`는 감지된 화자 라벨 수가 `attendeeNames` 수보다 많으면 초과분은 그냥
`화자 ${label}` 폴백 이름으로 남고, `AudioAnalysisModal`에서 사용자가 수동으로 이름을 입력해 정정하는
것만 가능(자동 처리 없음). 다음 세션에서 "자동으로 새 참석자로 등록할지", "명시적으로 게스트 표시할지"
등 방향을 사용자와 논의 필요.

## 6. 화자별 음성 프로필 저장 → 다음 회의에서 동일 인물 자동 인식

STT/화자 분리 후 각 화자의 음성 샘플로 개인 음성 프로필(임베딩)을 만들어 두고, 이후 회의에서 같은
사람이 말하면 자동으로 그 사람으로 인식/매핑. 지금은 회의마다 매번 처음부터 클러스터링하고 라벨↔이름
매핑도 매번 새로 함(영속화 없음).
- 기술적 연결고리: `whisperx.diarize.DiarizationPipeline.__call__`이 이미
  `return_embeddings=True` 옵션과 화자별 임베딩 벡터를 반환할 수 있다(`server/audio/sttLocalWhisperX.mjs`,
  `sttLocalWhisperCli.mjs`의 `diarizeWithPyannote`에서는 현재 이 옵션을 안 씀). 이 임베딩을 회의별이
  아니라 **참석자 단위로 영속 저장**(어디에 저장할지 - DB에 참석자별 임베딩 필드 추가 등)하고, 다음
  회의의 화자 임베딩과 코사인 유사도 비교해서 매칭하는 방식이 유력한 접근.
- Naver Clova는 이 방식이 안 통함(자체 API라 임베딩을 못 받음) - 로컬 WhisperX/Whisper CLI 경로에서만
  가능할 듯.

## 7. STT 오인식 수정 이력을 저장해서 같은 상황 재발 시 자동 치환

사용자가 STT 결과의 오인식을 수정하면(수정 UI가 아직 없을 수도 있음 - 확인 필요) 그 수정 이력(원문→
수정문)을 저장해뒀다가, 나중에 같은 오인식이 다시 나오면 자동으로 수정된 값으로 치환. 1번(약어 사전)과
비슷한 성격이지만 트리거가 다름(사전 등록 vs 사용자 수정 이력 누적) - 하나의 "치환 사전" 데이터 모델로
합칠 수 있을지도 검토 대상.
